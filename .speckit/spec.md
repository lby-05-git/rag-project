## User Scenarios & Testing *(mandatory)*

### User Story 1 - 研报上传与自动索引 (Priority: P1)

作为企业研究员，我希望上传 PDF 研报后系统自动完成文本解析、分块和向量化
存储，以便我能立即对研报内容进行提问。

**Why this priority**: 这是整个系统的基础——没有研报数据，问答和检索都
无从谈起。自动索引流程决定了用户体验的起点。

**Independent Test**: 上传一份包含明确事实性陈述的 PDF 研报，几秒后
查询该研报中的某个具体数据，验证系统是否返回正确结果并标注了来源。

**Acceptance Scenarios**:

1. **Given** 系统运行中，
   **When** 我上传一份 PDF 格式的研究报告，
   **Then** 系统自动解析文本、按策略分块、生成向量嵌入并存入 FAISS
   索引，整个过程无需人工干预。

2. **Given** 已上传多份研报，
   **When** 我查看研报列表，
   **Then** 系统展示所有已导入研报的名称、页数、导入时间及状态。

3. **Given** 我上传了一份非 PDF 格式或损坏的文件，
   **When** 系统尝试处理，
   **Then** 系统返回明确的错误提示，告知文件不支持或格式异常。

---

### User Story 2 - 智能问答与来源追溯 (Priority: P1)

作为企业研究员，我希望用自然语言提问，系统基于研报内容生成带来源引用的
回答，以便快速获取经得起验证的信息。

**Why this priority**: 智能问答是系统的核心价值，直接解决"研报太多读不完"
的痛点。来源引用保证可追溯性，是金融领域不可妥协的需求。

**Independent Test**: 提问一个研报中明确包含的事实性问题，验证回答
是否正确引用了来源（研报名称 + 页码），且引用内容与原文一致。

**Acceptance Scenarios**:

1. **Given** 系统中已导入多份研报，
   **When** 我输入"宁德时代 2025 年营收预测是多少"，
   **Then** 系统通过向量检索 Top-K 相关段落，组装 Prompt 后由
   Qwen2.5:0.5b 生成回答，并标注来源研报名称和页码。

2. **Given** 系统中已导入多份研报，
   **When** 我输入的问题在现有研报中找不到相关信息，
   **Then** 系统明确回复"未找到相关信息"，而非编造答案。

3. **Given** 已有一轮问答历史，
   **When** 我提出追问（不完整的问题，如前文基础上的"那净利润呢"），
   **Then** 系统结合历史上下文正确理解追问意图并给出回答。

---

### User Story 3 - 检索参数实时调节与效果观察 (Priority: P2)

作为高级用户或系统调优者，我希望在前端界面上实时调节 chunk_size 和
检索相似度阈值，并立即观察到对回答质量的影响，以便找到最优参数组合。

**Why this priority**: 不同的研报类型和问题形式适合不同的分块大小和
检索阈值。允许用户实时调节比固定参数更灵活，也能帮助积累最佳实践。

**Independent Test**: 在参数面板中调节 chunk_size 从 500 到 200，
用同一个问题测试两次，观察检索到的段落数量和回答质量的变化。

**Acceptance Scenarios**:

1. **Given** 我在问答界面中，
   **When** 我调整 chunk_size 滑块（范围 200-1000），
   **Then** 下一次查询使用新的分块大小（重新分块并嵌入）。

2. **Given** 我在问答界面中，
   **When** 我调整检索相似度阈值滑块（范围 0.1-1.0），
   **Then** 下一次查询只返回相似度高于该阈值的段落。

3. **Given** 我调整了任意参数，
   **When** 我提交新的问题，
   **Then** 回答下方显示当前使用的参数值（chunk_size、阈值），
   便于对比不同参数的效果。

---

### User Story 4 - 问答历史记录 (Priority: P3)

作为用户，我希望系统自动保存我的问答历史，以便回顾之前的分析过程和
结果，无需重复提问。

**Why this priority**: 历史记录提升使用便利性，但不影响核心问答功能，
可在 MVP 后迭代加入。

**Independent Test**: 完成一轮多轮对话后关闭页面，重新打开查看历史
记录是否完整保留。

**Acceptance Scenarios**:

1. **Given** 我与系统进行了多轮问答，
   **When** 我查看历史记录页面，
   **Then** 系统展示每次对话的时间、问题和回答，以及当时使用的参数。

2. **Given** 我在历史记录列表中，
   **When** 我点击某条历史记录，
   **Then** 系统还原该次对话的完整上下文，可继续追问。

---

### Edge Cases

- **空结果查询**：问题与研报无关时，系统回复"未找到相关信息"
- **超长查询**：超过 500 字符的查询应截断或清晰提示
- **并发查询**：同一时间多个查询请求应排队处理，不影响系统稳定性
- **参数极端值**：chunk_size=200 时需保证分块有语义完整性；
  similarity_threshold=1.0 时需优雅降级为"无匹配结果"
- **重复上传**：上传已存在的研报应提示重复，或选择覆盖/跳过
- **无研报时提问**：未上传任何研报时提问，应提示先上传研报

## Requirements *(mandatory)*

### Functional Requirements

**F1 — 研报管理**

- **FR-001**: 系统 MUST 支持通过前端页面上传 PDF 格式的研报文件
- **FR-002**: 系统 MUST 自动提取 PDF 文本内容，保留文件名和页码元数据
- **FR-003**: 系统 MUST 将提取的文本按 chunk_size 配置进行分块
- **FR-004**: 系统 MUST 调用 Ollama bge-large-zh-v1.5 生成文本块的
  向量嵌入
- **FR-005**: 系统 MUST 将嵌入向量存入本地 FAISS 索引
- **FR-006**: 系统 MUST 提供研报列表展示（名称、页数、导入时间、状态）
- **FR-007**: 系统 MUST 支持删除已导入的研报及其索引

**F2 — 智能问答**

- **FR-008**: 系统 MUST 接收用户自然语言问题，调用 FAISS 检索 Top-K
  相关段落
- **FR-009**: 检索结果 MUST 按相似度阈值过滤（可配置，默认 0.5）
- **FR-010**: 系统 MUST 将检索结果和问题组装为 Prompt，调用 Ollama
  Qwen2.5:0.5b 生成回答
- **FR-011**: 系统 MUST 在回答中标注每个引用点的研报名称和页码
- **FR-012**: 系统 MUST 支持多轮对话（追问），传递最近 3 轮对话历史作为上下文
- **FR-012a**: 系统 MUST 每次检索 Top-5 个最相关段落（K=5），超出相似度阈值的
  段落不传入 LLM Prompt

**F3 — 参数调节**

- **FR-013**: 前端 MUST 提供 chunk_size 滑块调节组件（范围 200-1000，
  步长 50，默认 500）
- **FR-014**: 前端 MUST 提供相似度阈值滑块调节组件（范围 0.1-1.0，
  步长 0.05，默认 0.5）
- **FR-015**: 参数变更后，下一次检索 MUST 使用新参数重新处理
- **FR-016**: 每次回答下方 MUST 显示当前使用的参数值

**F4 — 历史记录**

- **FR-017**: 系统 MUST 自动保存每次问答的完整记录（问题、回答、
  引用来源、使用参数、时间戳）
- **FR-018**: 系统 MUST 提供历史记录浏览界面，支持按时间排序
- **FR-019**: 用户 MUST 能点击历史记录恢复对话上下文继续追问
- **FR-020**: 系统 MUST 支持删除单条或全部历史记录

### Key Entities

- **Report（研报）**: PDF 文件。包含文件名、文件大小、页数、上传时间、
  处理状态（待处理/处理中/已完成/失败）。
- **Chunk（文本块）**: 研报分片后的文本片段。包含文本内容、所属研报 ID、
  起始页码、块序号、chunk_size 参数。
- **Embedding（向量嵌入）**: 文本块的 1024 维向量表示（bge-large-zh-v1.5
  输出维度）。与 Chunk 一一对应，存储在 FAISS 索引中。
- **QA Record（问答记录）**: 一次问答交互。包含问题、回答、引用来源列表、
  使用的参数（chunk_size、阈值）、时间戳、会话 ID 和轮次序号
  （用于多轮对话上下文截断策略）
- **Parameter Setting（参数设置）**: 用户当前的检索配置。包含 chunk_size、
  similarity_threshold，可作用于全局或单次查询。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上传一份 30 页的标准 PDF 研报，从上传到完成索引的
  全流程耗时 ≤ 3 分钟
- **SC-002**: 用户提交问题后，从发送到收到完整回答的响应时间 ≤ 10 秒
- **SC-003**: 对于研报中明确陈述的事实，回答准确率 ≥ 90%
  （人工验证 20 个已知答案的问题）
- **SC-004**: 对于与研报无关的问题，系统零幻觉率（100% 回复
  "未找到相关信息"）
- **SC-005**: 每次回答均正确标注引用来源（研报名称 + 页码），
  准确率 100%
- **SC-006**: 用户可通过前端界面完成完整流程：上传研报 → 提问 →
  查看回答 → 调节参数 → 再次提问，无需操作命令行
- **SC-007**: 所有数据存储于本地，不向任何外部服务发送研报内容
- **SC-008**: 历史记录保存后，重新打开页面仍可完整查看和恢复对话

## Assumptions

- 研报 PDF 以文本型为主（非扫描图片型），如有扫描件需要额外的 OCR
  预处理（当前版本不做）
- Ollama 已在本机安装并运行，Qwen2.5:0.5b 和 bge-large-zh-v1.5
  模型已通过 `ollama pull` 下载
- 单次查询涉及的研报数量不超过 20 份（超出需手动指定范围）
- 系统单机运行，无需考虑多用户并发和数据隔离
- 用户通过浏览器访问前端（默认 localhost 部署）
- 用户具备基本的 Python 和 Node.js 环境配置能力
- Qwen2.5:0.5b 的上下文窗口限制为 32K tokens；Prompt 组装策略为
  Top-5 检索段落 + 最近 3 轮对话历史，超出则截断最早的历史轮次
