# RAG 项目宪法

## 核心原则

### 一、规范驱动开发（Spec-Driven Development）

每个功能必须从书面规范开始。规范必须在实现之前定义用户故事、验收标准
和范围边界。没有规范就没有代码——这是 Spec Kit 方法论的基石。

- 所有功能遵循生命周期：规范 → 方案 → 任务 → 实现 → 评审
- 规范必须按用户故事可独立测试
- 范围变更需要在继续实现之前修订规范

**理由**：防止无边界的工作，确保编码前达成一致，为测试和评审提供契约。

### 二、文档优先的 RAG 流水线

数据导入、分块、嵌入、存储、检索、生成构成一条定义清晰的流水线。每个
阶段必须可独立运行和测试。

- 文档处理必须保留来源追溯信息（元数据、页码、原始格式）
- 分块策略必须明确、可配置、可审计
- 检索质量必须可度量（召回率、精确率、MRR）
- 生成结果必须引用检索步骤中的来源
- 中文金融文档是主要领域——流水线设计必须考虑 CJK 分词、中英文混排
  和金融术语的处理

**理由**：RAG 系统的可信度取决于其流水线的可追溯性。对于金融数据，从
源文档到生成答案的全程可追溯是不可妥协的。

### 三、测试优先（不可妥协）

在编写实现代码之前，必须先编写测试并确认其失败（红-绿-重构）。这适用
于每一个流水线组件。

- 检索测试必须验证对已知查询能返回正确分块
- 集成测试必须端到端地演练完整流水线
- 黄金数据集（已知文档→已知答案对）必须持续维护
- 边界情况必须包括：空结果、歧义查询、格式错误的输入以及中英文跨语言
  查询
- 每个组件必须度量测试覆盖率；回归问题阻止合并

**理由**：RAG 系统以静默方式失败（错误答案但看起来合理）。测试优先的
纪律能在这些失败影响生产之前将其捕获。

### 四、模块化与可组合设计

每个 RAG 组件（导入、分块、嵌入、检索、生成）是一个具有明确定义接口的
可替换模块。没有模块依赖另一个模块的内部实现。

- 组件通过明确定义的契约（Python 协议/抽象接口）通信
- 组件必须可在不修改其消费者的情况下替换
- 共享模式（分块格式、查询格式、结果格式）必须进行版本管理
- 必须优先选择满足当前已知需求的最简单设计（YAGNI）

**理由**：RAG 生态发展迅速——模块化设计允许升级嵌入模型、向量存储或
LLM 后端而无需重写整个系统。

### 五、可观测性与质量保证

每个 RAG 操作必须可观测。延迟、检索质量和生成质量必须被度量和记录。

- 结构化日志记录要求：导入批次、查询耗时、检索到的分块 ID、生成的
  回答文本
- 每次查询必须计算检索质量指标（命中率、MRR、NDCG）
- 生成质量必须抽样检查幻觉、相关性和来源忠实度
- 必须定义并监控性能预算（每次查询的 p95 延迟、每批文档的最大内存）
- 所有可观测性数据必须可用于离线分析和仪表板展示

**理由**：没有可观测性，RAG 系统就是一个黑箱。质量退化（分块损坏、
嵌入过期、提示漂移）在用户报告之前是不可见的。

## 技术栈与环境

### 语言与运行时
- **Python 3.12+** 用于所有流水线组件
- 虚拟环境（`.venv/`），通过 `requirements.txt` 或 `pyproject.toml`
  锁定依赖版本

### 核心依赖
- 向量数据库：用于嵌入存储和相似性搜索
- 嵌入模型：支持中文文本（双语/多语言）
- LLM 后端：用于答案生成（API 或本地）
- 文档解析库：支持含 CJK 的 PDF 提取
- 框架选择（LangChain、LlamaIndex 或自研）必须在规范中说明理由

### 数据
- 原始 PDF 存放在 `data/`（git 已忽略——运行时加载）
- 处理后的分块、嵌入和索引存储在仓库之外
- 不提交密钥或凭据；使用 `.env` 存放 API 密钥

### 测试与质量
- `pytest` 作为测试运行器
- 黄金测试数据集与代码一起保存以确保可重现性
- 检索准确率基准测试作为 CI 的一部分运行

## 开发工作流与质量门禁

### 功能生命周期
1. **规范**（`/speckit-specify`）—— 编写含用户故事和验收标准的规范
2. **方案**（`/speckit-plan`）—— 设计架构、数据模型和契约
3. **任务**（`/speckit-tasks`）—— 从设计方案生成有序的任务列表
4. **实现**（`/speckit-implement`）—— 按任务构建，测试优先
5. **评审** —— 代码审查和宪法合规性检查
6. **收敛**（`/speckit-converge`）—— 验证实现与规范一致

### 质量门禁
- **宪法检查**：每个方案必须在第 0 阶段调研之前通过宪法合规性检查，
  并在第 1 阶段设计之后再次检查
- **测试门禁**：所有测试必须通过才能合并；新功能需要新测试
- **评审门禁**：需要进行代码评审；至少一名评审人必须验证原则合规性

### 分支管理
- 功能分支：`###-feature-name` 对应每个功能
- 在每个逻辑任务或任务组完成后提交
- 提交消息必须引用任务 ID

## 治理

本宪法优先于所有其他项目实践。修宪需要：

1. **提案**：在规范或 issue 中记录拟议变更
2. **评审**：宪法变更必须经过评审和批准
3. **迁移计划**：任何变更必须包含现有功能配合的迁移计划
4. **版本号递增**：
   - MAJOR：不兼容的原则删除或重新定义
   - MINOR：新增原则或实质性扩展指导
   - PATCH：澄清、措辞、拼写修正
5. **文档**：更新本文件，更新同步影响报告，提交

所有 PR 和评审必须验证宪法合规性。当发生宪法违反时，复杂度必须在方案
的"复杂度追踪"部分进行说明。`.speckit/constitution.md` 是项目治理的
唯一真实来源。
